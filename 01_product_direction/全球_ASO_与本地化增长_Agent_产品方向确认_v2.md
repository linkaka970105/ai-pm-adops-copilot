## **项目概述**

**目的：** 解决“白帽 ASO 能不能被服务化、卖出去、交付好、复盘并复用”这一产品方向问题。产品由两面组成：

```text
客户侧：服务入口、目标/资料提交、诊断解释、交付物查看、审批、状态和结果复盘
内部侧：服务项目、专家路由、Agent 任务、证据、版本、QA、SLA、履约和学习
```

两面共享一组受控对象：`Customer Account`、`App Workspace`、`App×Store×Country`、`Service Project`、`Service Package`、`Growth Task`、`Deliverable`、`Evidence Object`、`Listing Version`、`Review`、`Approval`、`SLA`、`Validation`、`Outcome Report`、`Learning`。

### 产品方向的三种可选形态

| 方案 | 产品形态 | 可以解决什么 | 主要缺口 | 方向判断 |
| --- | --- | --- | --- | --- |
| 方案 A：AI 文案/本地化工具 | 生成标题、描述、翻译和素材文案 | 提高单个交付环节速度 | 无法承接诊断、范围、审批、责任和复购 | 作为能力组件，不单独立项 |
| 方案 B：ASO 数据分析 Copilot | 帮内部人员查询数据、写分析和方案 | 提高内部研究与报告效率 | 客户不可见，服务边界和交付状态不标准 | 作为内部 Delivery OS 的子能力 |
| 方案 C：ASO Growth Service Agent | 客户入口 + 服务目录 + 内部交付 OS + 受控 Agent | 把白帽服务变成可购买、可履约、可验证、可复购的产品 | 需要服务运营、权限、证据、审批、SLA 和安全治理 | **推荐方向** |

### 产品描述

> **产品公式：** 为 `[需要外部 ASO 白帽服务的 App 开发者、增长负责人和后续代理商]` 提供 `[客户侧服务入口 + 内部交付 OS + 受控 Agent]`，通过 `[结构化受理、只读诊断、证据化交付、专家 Review、客户 Approval 和结果复盘]`，解决 `[客户不知道买什么、内部交付依赖个人经验、版本/责任/结果不可追溯]`，实现 `[白帽 ASO 服务的标准化交付和持续增长学习]`。

客户提交 App、商店、国家、目标、产品事实和授权信息；系统判断资料完整性与风险，再匹配诊断、商店页优化、本地化、评论洞察、创意 Brief 或验证复盘服务。内部专家通过 Delivery OS 使用 Agent 处理检索、整理、生成、校验和项目协同；客户查看依据、修改并批准版本；外部发布和实验由客户或授权人工执行；结果只按证据等级报告。

### 核心问题定义

白帽 ASO 服务的核心问题不是“能不能写出一段文案”，而是一个跨购买、交付和复盘的服务问题：

```text
客户有 App、目标市场和增长诉求
→ 但不知道问题是什么、应该买哪种服务、要提供什么资料
→ 内部团队接到需求后依赖个人经验拆解、研究、翻译和交付
→ 客户审批、实际执行、结果窗口和干扰因素不在同一条链上
→ 服务结束后无法形成可解释的下一项任务或复购理由
```

产品必须能回答：

- 本次服务的目标、范围、交付物和不包含什么？
- 结论基于什么证据，数据口径、时间、市场和局限是什么？
- 哪些内容需要 ASO、母语、设计、客户或合规人员确认？
- 哪个版本由谁批准、谁发布、SLA 如何计时？
- 结果是观察、实验支持、专家判断还是无法归因？
- 下一项服务来自什么未解决问题，而不是来自不可验证的效果承诺？

### 产品定位与边界

#### 产品定位

```text
ASO Growth Service Agent
= 白帽 ASO 服务的客户入口
  + 内部服务交付 OS
  + Evidence Object / Review / Approval / Validation / Learning
  + Policy Gate 与人工责任链

≠ 通用翻译工具
≠ 单点关键词工具
≠ 排名/下载/评分/评论保证工具
≠ 刷榜、虚假安装、虚假评论或诱导评分工具
≠ 未授权数据采集或默认自动发布系统
```

#### 第一阶段包含

- 客户 Account、App Workspace、商店/国家/语言和角色权限；
- 服务请求、资料补全、风险预检和 Service Package 匹配；
- 可交付的白帽诊断、商店页迭代、本地化审校、评论/VoC 洞察、创意 Brief；
- `Evidence Object`：来源、时间、市场、语言、口径、支持主张、置信度、局限和可见性；
- 内部 `Service Project → Growth Task → Deliverable` 任务链；
- 专家 Review、客户 Approval、SLA、变更、升级和审计记录；
- Listing Version、实际执行对账、Validation Plan 和 Outcome Report；
- 人工反馈、错误案例、客户授权和适用范围受控的 Learning。

#### 第一阶段不包含

- 自动购买安装、刷榜、虚假评论、诱导评分、排名保证或规避平台检测；
- 自动登录并发布商店页、自动创建/停止实验、自动修改广告预算/出价；
- 用第三方估算、单次前后变化或模型判断冒充确定的业务因果；
- 未经客户授权使用后台、用户、竞品或历史项目敏感数据；
- 代替客户、母语专家、设计、法务或平台承担最终判断和责任；
- 在客户尚未理解范围和责任时，以“AI 自动增长”作为销售承诺。

#### 一期优先用户与选择依据

> **一期优先用户：** 已有 App 且存在明确增长停滞，或准备进入单一新市场的中小开发者/增长负责人。

## **业务背景与问题定义**

### 现有业务/行业背景

- 用户输入确认：现有 ASO 业务主要包含黑帽和少量白帽；产品调整方向是优先把白帽业务 Agent 化，提高白帽服务交付成效，并逐步将能力集成到对外 ASO 服务。
- 白帽服务的交付对象通常不是一个独立功能，而是一个 App 在特定商店、国家、语言和时间窗口下的增长任务。
- 客户购买的是判断、交付物、协作和责任；内部需要承担研究、专家、母语、设计、客户成功和结果复盘。
- 公开竞品已经覆盖数据、关键词、评论、元数据、素材、实验或 AI；新产品不应以“又一个 ASO 数据看板”作为主线。
- 黑帽/操纵类服务与白帽服务在销售口径、数据、权限、Agent 工具和知识回流上必须隔离；具体组织责任待业务 owner 确认。

### 核心问题识别

#### 问题一：客户需求不可直接转成可售卖服务

“帮我提升排名”“帮我做本地化”“帮我优化 ASO”不是可执行的服务定义。客户需要目标、商店/市场、现状、资料、交付物、审批人、时间、执行责任和结果边界。没有 Service Package 和受理门槛，销售承诺会超出交付能力。

#### 问题二：内部交付效率依赖个人经验

研究、文案、本地化、创意、QA、客户沟通和复盘由不同角色完成。若 Agent 只生成内容而不处理证据、范围、任务路由、版本、SLA 和返工原因，整体项目人时不会下降，甚至会增加审核负担。

#### 问题三：客户不可见，服务信任难建立

客户需要知道建议依据、缺什么资料、为何这样做、哪个版本待审批、谁执行和怎样判断结果。只交付一份黑盒报告或聊天记录，无法支撑外部服务和复购。

#### 问题四：结果和责任容易被混淆

商店排名、下载、评分、转化会受到产品、广告、版本、季节和平台变化影响。若没有实际版本、时间窗口、干扰因素和证据等级，服务结果会被夸大，客户争议和平台风险都会上升。

#### 问题五：白帽主线容易被高风险需求吞没

如果产品用“快速提升排名/下载/评论”获客，Agent 会被要求提供操纵细节。白帽方向需要在入口、报价、生成、审核、执行和学习处设 Policy Gate，拒绝、升级并提供合规替代服务。

### 问题量化与机会评估

当前没有可直接使用的真实基线，因此一期只验证服务过程和商业信号：

| 价值层 | 首要指标 | 说明 |
| --- | --- | --- |
| 客户价值 | 服务匹配认可率、Approval 完成率、客户主动继续任务率 | 客户是否认可过程型白帽价值 |
| 交付效率 | 首次可审时长、总交付人时、返工轮次、SLA 达成率 | 是否真的降低端到端成本 |
| 质量 | Evidence 覆盖率、产品事实错误率、专家采纳率、Outcome 完整率 | 是否能交付可信内容 |
| 商业 | 首包购买率、周期复购、服务毛利、超范围工时 | 是否可持续售卖 |
| 安全 | 高风险识别/拒绝/升级正确率、越权和隔离事件 | 红线事件必须为零 |

### 问题发生频率

通过客户访谈、内部历史任务回放和 concierge 试点采集：

| 观察对象 | 需要记录 |
| --- | --- |
| 受理 | 资料补件次数、需求澄清轮次、风险拒绝/升级数量 |
| 交付 | 研究、生成、专家 Review、客户等待、返工和报告时间 |
| 版本 | 版本修改、审批、实际发布和执行错配次数 |
| 结果 | 观察窗口、指标采集、干扰因素和无法归因原因 |
| 商业 | 报价异议、范围变更、购买/继续服务/取消原因 |

### 问题影响范围

1. 客户买不到清晰可比较的服务；
2. 内部团队重复整理、排期、沟通和返工；
3. 专家经验无法形成受控的组织资产；
4. 销售、交付、客户成功和合规对责任边界理解不一致；
5. 结果争议会削弱白帽服务信任，甚至把业务重新推向高风险承诺；
6. 跨 App、市场和语言的学习无法安全复用。

### 当前解决方式的成本

```text
客户经理口头接单
→ 运营人工澄清目标和范围
→ 多工具查询和复制资料
→ 专家、本地化、设计分散交付
→ 客户在聊天/邮件中修改和审批
→ 人工发布、等待和写报告
→ 下次项目重新整理，难以比较成本和结果
```

这条链的主要浪费不是单个环节，而是上下文反复搬运、责任不清、版本错配、返工不可解释和结果无法沉淀。

## **AI 技术应用方向初步探索**

**目的：** 让 AI 服务于“受理—交付—复盘”而不是替代 ASO 专家或销售承诺。

### 为什么需要 AI？

1. 客户需求、产品事实、商店页、评论、竞品、设计素材和历史项目是多语、非结构化和多模态信息，人工整理成本高；
2. 服务匹配、任务拆解、证据关联、版本比较、缺口提醒、报告初稿和状态问答适合由 Agent 处理；
3. AI 可以在同一项目上下文中帮助客户和内部团队理解“为什么做、做到哪、还缺什么、谁审批、如何复盘”；
4. AI 的增量是降低服务交付成本和提高可解释性，不是自动保证商店结果。

### AI、规则和人工的职责边界

| 组件 | 负责 | 禁止/不负责 |
| --- | --- | --- |
| 客户侧 Agent | 受理、追问、资料缺口、诊断解释、服务匹配、状态和审批提醒 | 代客户签约/审批、承诺排名/下载、自动发布 |
| 内部交付 Agent | 任务拆解、证据检索、聚类、草案、QA 提示、版本差异、报告初稿 | 扩大范围、绕过 Gate、未经授权调用数据或外部写入 |
| 规则/Policy Gate | 权限、禁用请求、产品事实、字符/字段、版本和审批状态 | 代替复杂市场、文化、品牌和法务判断 |
| 数据连接器 | 公开页、评论、关键词、授权后台快照 | 把估算直接写成真实指标或因果 |
| 专家/客户 | 策略、母语、产品事实、品牌、审批、发布、实验和结论采纳 | 把 AI 产出当作平台保证 |

### 初步技术路径设想

```text
结构化 Service Intake
+ 受控工作流编排
+ 公开/授权数据连接器
+ Evidence Object 与产品事实库
+ 多语/多模态模型
+ 规则和 Policy Gate
+ 专家 Review 与客户 Approval
+ Validation / Outcome / Learning
```

先做单一服务链的可靠工作流，不做多个 Agent 自由讨论和无边界自动执行。

### 技术架构设想

```text
Account / App / Store / Country / Goal / Authorization
↓
完整性检查 + Policy Gate
↓
Service Package 匹配与范围确认
↓
公开/授权数据快照 + Product Fact Store
↓
Evidence Object：来源/时间/口径/置信度/局限/可见性
↓
Service Project → Growth Task → Expert Route → SLA
↓
Deliverable：诊断/Listing/Creative/Localization/Validation
↓
内部 Review → 客户 Approval → 人工执行
↓
Outcome Report → Learning → 下一任务/续费/停止
```

| Validation / Outcome | P1 | 实际版本、窗口、指标、干扰和证据等级 |

### 可落地的 3 个子场景

#### 子场景一：客户诊断与服务匹配

客户提交 App、市场、目标和当前问题。Agent 先判断是否有足够产品事实、公开/授权数据和审批资源，再输出诊断预览、风险和服务包候选；不能满足条件时输出补件或人工咨询，而不是生成泛化报告。

#### 子场景二：内部交付与客户审批

获批服务范围自动生成 Growth Task。Agent 负责检索、整理、聚类、草案、版本差异和检查；ASO、母语、设计专家负责专业判断；客户看到来源、限制、修改轮次、风险和批准版本，执行仍由客户或授权人工完成。

#### 子场景三：结果复盘与复购

系统核对实际发布的 Listing Version，记录时间窗口、数据源、产品/广告/季节/平台变化等干扰，生成 Outcome Report。下一项服务来自未解决任务或可靠 Learning，若无法归因就明确写“无法判断”，不生成效果承诺。

### 可行性与风险评估

### **数据可行性**

| 数据 | 一期用途 | 前置条件 | 不可越过的边界 |
| --- | --- | --- | --- |
| 公开商店页/评论 | 诊断、竞品、用户语言和市场信号 | 记录时间、市场和采集方式 | 不把样本当总体，不处理不必要个人信息 |
| 客户产品事实 | 生成和校验交付物 | 客户确认、版本化、可撤回 | 不编造不存在的功能或承诺 |
| 客户授权商店/分析后台 | 版本、指标、实验和结果 | 明确授权、租户隔离、最小权限 | 不跨客户读取、导出或训练外部模型 |
| 第三方数据/API | 补充关键词/竞品/趋势 | 合法许可、口径和费用 | 不把估算冒充真实平台指标 |
| 历史交付和结果 | 专家反馈、Badcase、Learning | 脱敏、适用范围和客户授权 | 不把一客户结论自动外推 |

### 技术可行性

- 多语模型适合需求/评论聚类、本地化草案和解释；
- 多模态模型适合商店素材和图文一致性检查；
- 结构化工作流、规则和 Schema 可以稳定处理服务状态、版本和审批；
- RAG/事实库可以提供产品、品牌、政策和术语引用；
- 一期可以不训练排名预测、不写入商店、不自动控制广告；
- 评测重点应是任务路由、证据充分、事实正确、风险拒答、专家采纳和端到端人时。

### 业务风险

| 风险 | 表现 | 处理 |
| --- | --- | --- |
| 黑白帽冲突 | 高风险预算被导入白帽服务 | 受理前 Gate、拒绝/升级、隔离服务线、销售口径统一 |
| 期望错配 | 客户以为 Agent 会发布或保证结果 | 服务包、责任、Approval 和执行状态显式化 |
| 证据/事实错误 | 生成虚假指标、功能、翻译或引用 | 事实库、来源校验、专家 Review、Badcase 回归 |
| 数据和租户风险 | 读取错误客户或将资料带入 Learning | ACL、缓存/导出隔离、审计、删除和红队 |
| 服务毛利风险 | Agent 生成多但专家返工更多 | 以端到端人时、返工、SLA 和毛利为准，必要时降级 AI |
| 结果争议 | 将相关性、前后变化写成因果 | 版本/窗口/干扰/证据等级和无法归因状态 |
| 平台政策变化 | 规则、实验或数据权限变化 | 官方规则版本、失效提醒和人工复核 |

### 初步成功标准

#### Concierge/PoC

- 能在一个 App、一个商店、一个或两个市场完成一次白帽服务闭环；
- 客户能理解范围、交付物、证据、风险、Approval 和执行责任；
- Agent 至少降低资料整理、任务拆解、版本比较或报告编排的人时；
- 专家可以快速发现并修正错误，且所有重要主张可追溯；
- 高风险请求被正确拒绝/升级，不产生规避细节；
- 不宣称排名、安装、评论、评分、收入或 ROI 结果。

#### 真实试点

- 建立首次可审时长、总交付人时、返工、SLA、Approval 和 Outcome 基线；
- 客户愿意购买或继续一个明确范围的服务包；
- 实际执行版本、窗口和干扰可对账；
- Learning 带适用范围和反例，不跨租户自动迁移；
- 红线放行、越权和跨客户泄露事件为零。

## **业务流程/场景分析**

**目的：** 用“服务受理—交付—审批—验证—复购”的业务链展示 Agent 的真实增量。

### 当前业务流程图

```mermaid
flowchart LR
    A[客户提出模糊目标] --> B[销售/客户经理人工澄清]
    B --> C[内部人员分散研究和拆解任务]
    C --> D[专家/本地化/设计分别交付]
    D --> E[聊天/文件往返修改]
    E --> F[客户或内部人员执行]
    F --> G[人工观察和报告]
    G --> H[结果、返工和经验未形成统一服务状态]
```

### 引入 AI 后的理想业务流程图

```mermaid
flowchart LR
    A[客户提交App/市场/目标/资料] --> B[完整性与授权检查]
    B --> C[Policy Gate]
    C --> D[诊断与Service Package匹配]
    D --> E[Service Project/SLA/责任确认]
    E --> F[Evidence与Agent辅助交付]
    F --> G[专家Review/QA]
    G --> H[客户Approval/退回]
    H --> I[客户或授权人工发布/验证]
    I --> J[Outcome Report/归因边界]
    J --> K[Learning/下一任务/复购/停止]
```

AI 介入的重点是：受理补全、服务匹配、证据整理、任务路由、草案和质量提示、版本对比、状态问答、报告编排和学习候选。人工保留：服务承诺、策略判断、母语/品牌、客户审批、外部发布、实验和最终合规责任。

## 本轮需要重点讨论的 6 个问题

1. **一期首客：** 是否先选择已有 App、增长停滞或进入单一新市场的中小开发者/增长负责人？
2. **首包定义：** 是否先卖“白帽健康诊断”或“新市场诊断与商店页迭代”，并明确交付物和不承诺事项？
3. **服务组织：** 真实业务中谁负责销售、ASO、母语、设计、客户成功、合规和外部执行？
4. **白帽/黑帽隔离：** 存量高风险业务是否独立组织、账号、数据、权限、销售口径和学习回流？
5. **数据与结果：** 一期能获得哪些公开/授权数据，哪些指标能形成真实版本和观察窗口，谁拥有结果解释权？
6. **MVP Gate：** 在什么人时、质量、安全和客户信号下，才扩大到周期服务、多市场、代理商、API/白标或受控自动化？

在以上问题和首个 concierge 试点完成前，本文件只作为产品方向基线，不进入大规模工程化，也不对外承诺增长结果。

## **项目概述**

**目的：** 明确 ASO 白帽服务产品化的目标客户、服务闭环、AI 作用边界、一期验证范围和后续 PRD 重写依据。产品主线不再是“内部运营人员使用的分析工具”，而是：

```text
客户服务入口
→ 只读诊断与服务匹配
→ 专家/Agent 协同交付
→ 客户 Review 与 Approval
→ 客户或授权人工执行
→ Validation / Outcome Report
→ Learning / 续费 / 复购
```

共享的业务内核包括 `Customer Account`、`App Workspace`、`App×Store×Country`、`Service Project`、`Growth Task`、`Service Package`、`Deliverable`、`Evidence Object`、`Listing Version`、`Review`、`Approval`、`SLA`、`Validation`、`Outcome Report` 和 `Learning`。

### 产品方向的三种可选形态

| 方案 | 产品形态 | 优点 | 局限 | 结论 |
| --- | --- | --- | --- | --- |
| 方案 A：本地化文案助手 | 输入原文，生成多语言标题、短描述和长描述 | MVP 轻、容易演示 | 与通用翻译/写作工具差异小，不能证明服务价值 | 不单独立项，可作为交付组件 |
| 方案 B：内部 ASO 分析 Copilot | 汇总关键词、竞品和评论，供运营人员输出报告 | 能提升内部研究效率 | 客户看不到范围、责任、审批和履约状态，容易停在报告生成 | 保留为内部交付能力，不作为最终产品形态 |
| 方案 C：ASO Growth Service Agent | 客户入口 + 内部交付 OS，把诊断、服务包、专家交付、审批、验证和复购连接起来 | 直接承接白帽业务服务化，能形成数据和商业闭环 | 需要租户、权限、SLA、证据治理、人工审核和服务运营 | **推荐方向** |

### 产品描述

> **产品公式：** 为 `[需要白帽 ASO 服务的 App 开发者/增长负责人]` 提供一款 `[客户侧服务入口 + 内部服务交付 OS + 受控 Agent]`，通过 `[只读数据、Evidence Object、工作流编排、规则校验和人工审核]`，解决 `[ASO 诊断、方案交付、客户审批和结果复盘分散且不可追溯]`，实现 `[可售卖、可履约、可验证、可复用的白帽增长服务]`。

客户提交 App、商店、市场、目标和授权信息后，系统先做数据完整性与 Policy Gate 检查，再提供诊断和服务包匹配。内部 ASO 团队在交付工作台中完成关键词、评论、Listing、创意和本地化工作；客户可看到证据、版本差异、风险和待审批动作；发布与实验仍由客户或授权人工执行。结果以证据等级报告，不承诺排名、下载、评分、评论或收入结果。

### 核心问题定义

> 原有内部 ASO Agent 的核心问题是“如何让运营人员更快形成增长决策”。新的外部服务产品还必须解决“客户为什么购买、内部如何履约、客户如何审批、结果如何复盘和续费”。

```text
客户有 App、市场和增长目标
但不知道应该购买哪一种 ASO 服务、需要提供什么资料、交付依据是什么；
内部团队能做研究和文案，
但服务范围、交付物、责任人、版本、审批、SLA 和结果归因分散在表格、聊天和人工经验中；
因此数据很难稳定转化为客户可理解、可批准、可执行、可复盘的白帽服务。
```

产品要回答的不是“这句话怎么翻译”，而是：

- 这个 App 在该商店、国家和语言中最值得解决的增长任务是什么？
- 当前结论使用了哪些公开或授权数据，口径、时间和局限是什么？
- 应该购买诊断、商店页迭代、本地化、创意 Brief 还是结果复盘服务？
- 哪些内容已经可以交付，哪些需要专家、母语人员或客户补充？
- 客户要审批哪个版本，谁负责执行，SLA 从哪里开始计时？
- 结果能否归因，哪些只是观察，哪些可以形成下一轮 Learning？

### 产品定位与边界

#### 产品定位

```text
ASO Growth Service Agent
= 客户侧白帽服务入口
  + 内部 ASO 服务交付 OS
  + Evidence Object / Policy Gate / Review / Validation / Learning 内核

≠ 通用翻译工具
≠ 单纯关键词查询工具
≠ 排名、下载、评分或收入保证工具
≠ 自动刷榜、虚假安装、虚假评论或诱导评分工具
≠ 无授权数据采集和自动发布系统
```

#### 第一阶段包含

- 客户 Account、App Workspace 和 `App×Store×Country` 工作区；
- 服务请求、资料补全、只读诊断和 Service Package 匹配；
- 市场与竞品研究、公开评论洞察、关键词搜索意图和 Listing 诊断；
- 标题、短描述、长描述、更新说明、本地化草案和 Creative Brief；
- Evidence Object：来源、时间、市场、语言、口径、支持主张、置信度和局限；
- Service Project、Growth Task、Deliverable、SLA、Review、Approval 和审计日志；
- 事实、品牌、字符、文化和平台规则检查；
- 人工执行前的版本对账、Validation Plan、Outcome Report 和 Learning 候选；
- 客户/专家对 AI 产出的修改、采纳、驳回和原因反馈。

#### 第一阶段不包含

- 自动购买安装、刷榜、虚假评论、诱导评分、评论操纵或排名保证；
- 设计规避 Apple/Google 检测或提升黑帽执行效果的方案；
- 自动登录并发布商店页、自动创建/停止实验、自动写入广告预算或出价；
- 未经授权使用客户、用户或竞品敏感数据；
- 用一次前后变化证明确定因果，或将模拟数据写成真实增长结果；
- 代替客户、母语专家、法务或平台承担最终决策和责任。

#### 一期优先用户

> **建议 + 待验证假设：** 一期选择“已有 App 且存在明确增长停滞，或有单一新市场进入需求的中小开发者/增长负责人”。优先一个 App、一个商店、一个或两个市场，并要求客户能提供产品事实、公开或授权数据、审批人和人工发布/验证资源。

选择依据：决策链较短、结果有一定历史基线、资料和权限边界容易控制、服务过程和交付成本可观察。代理商价值高，但多租户、白标、责任分摊会掩盖白帽服务本身是否成立，因此放到二期/三期验证。

## **业务背景与问题定义**

### 现有业务/行业背景

- **用户输入确认的业务变化：** 原有 ASO 业务主要包含 ASO 黑帽和少量白帽；当前希望优先把白帽业务通过 Agent 服务化，提高白帽交付成效，再以合规白帽服务建立客户关系和复购基础。
- **行业场景：** App 经过广告、自然搜索或外部推荐后，仍需要在 App Store/Google Play 商店页完成发现、理解、信任和下载决策；商店页同时承担搜索、定位、本地化和转化承接。
- **服务参与方：** App 开发者/发行商、增长与 ASO 团队、本地化和设计协作方、ASO 数据平台、代理商/托管服务商、Apple/Google 平台。
- **结构性变化：** 竞品已经覆盖关键词、评论、元数据、素材、实验和部分 AI。新的竞争单位不是“有没有数据”，而是能否把客户目标、证据、服务范围、交付、审批、执行和复盘串成可买、可履约的白帽服务。
- **事实边界：** 真实客户规模、白帽业务占比、服务价格、交付人时、历史结果和黑帽存量线的组织方式仍需业务 owner 补充。

### 核心问题识别

#### 问题一：客户目标与内部 Growth Task 没有连接

客户需要的是“新市场诊断”“商店页迭代”或“持续监测”，而内部团队通常以关键词任务、评论分析或文案任务接单。若没有 `Service Project`、`Service Package`、`Deliverable` 和 `SLA`，客户无法理解买到什么，内部也难以界定责任。

#### 问题二：数据、证据和建议无法稳定追溯

公开商店页、评论、关键词、竞品、产品事实和授权后台数据分散在不同工具。AI 生成的建议若没有来源、时间、口径、置信度和局限，就无法在客户 Review 中解释，也无法在结果复盘时区分事实、推断和假设。

#### 问题三：交付物、版本、审批和执行责任容易错位

文案、截图 Brief、本地化版本和实验方案常在表格、聊天和文件夹中流转。客户可能审批了一个版本，执行时却使用了另一个版本；内部可能以为已发布，客户却仍在等待审核。需要 `Listing Version → Review → Approval → Actual Execution → Validation` 的可追踪链。

#### 问题四：白帽服务与高风险存量业务的口径冲突

如果服务入口仍以排名、安装、评分或评论结果吸引客户，白帽产品会承担合规和声誉风险。黑帽/操纵类请求必须在受理前由 Policy Gate 识别、拒绝或升级；若公司保留存量高风险业务，只能作为隔离的人工服务线，不进入 Agent 主流程、数据集和学习回流。

#### 问题五：结果归因和续费依据不足

排名、下载、商店转化、广告、产品版本、季节和平台算法同时变化。不能把一次前后变化写成文案或服务包的确定因果。Outcome Report 需要记录实际版本、观察窗口、数据源、干扰因素、验证路径和证据等级，续费应建立在下一项可解释的增长任务上。

### 问题量化与机会评估

当前没有已确认的真实服务基线。第一阶段只验证以下四类价值，不预设排名、下载、评分、评论或收入目标：

| 价值层 | 需要建立的基线 | 目标方向 |
| --- | --- | --- |
| 产品效率 | 输入完整到首次可审交付的时间、客户补件轮次、状态查询次数 | 降低重复整理和交接成本 |
| 交付质量 | Evidence 覆盖率、产品事实错误率、专家实质返工率、一次通过率 | 提升可解释和可执行程度 |
| 客户价值 | 诊断到服务咨询/购买、Approval 完成、SLA 达成、Outcome Report 完整 | 验证客户是否认可过程型价值 |
| 商业价值 | 首包购买、继续服务、复购、服务人时和毛利 | 验证可售卖和可持续交付 |
| 安全质量 | Policy Gate 识别/拒绝/升级正确率、越权和跨租户事件 | 红线事件为零 |

### 问题发生频率

建议通过 5–8 名目标客户、3–5 名内部交付人员和 2–3 个真实/脱敏任务建立基线：

| 待验证问题 | 需要采集的基线 |
| --- | --- |
| 一个诊断或商店页迭代交付需要多久 | 从受理、补件、研究到首次可审和结项的时间 |
| 资料和证据搬运是否重复 | 使用工具数、网页/表格数量、重复查询和复制次数 |
| 服务范围是否经常变化 | 变更次数、变更原因、超范围工时 |
| 客户审批是否造成瓶颈 | 审批等待、修改轮次、退回原因 |
| 本地化和专家返工是否严重 | 语言、产品事实、品牌、文化、策略错误分类 |
| 结果是否可复盘 | 实际版本、窗口、指标口径、干扰因素和证据等级完整率 |

### 问题影响范围

1. **外部客户：** 不知道买什么、如何提供资料、怎样判断服务是否有价值。
2. **ASO/增长交付团队：** 研究、复制、整理和报告耗时，交付质量依赖少数专家。
3. **本地化和设计团队：** 缺少评论、关键词、产品事实和目标假设上下文，容易返工。
4. **服务经理/客户成功：** 难以管理范围、SLA、审批、升级、变更和复购。
5. **业务负责人：** 难以区分白帽服务收入、黑帽存量线和产品化交付成本。
6. **平台与最终用户：** 不合规的增长请求可能影响 App 账号、商店生态和用户信任。

### 当前解决方式的成本

```text
销售或客户经理接收模糊需求
→ ASO 运营人工查工具、竞品和评论
→ 复制到表格/文档并凭经验形成建议
→ 翻译、本地化、设计和专家反复修改
→ 客户在聊天中审批，版本和责任不清
→ 人工发布或观察，报告与实际版本对不上
→ 下次项目重新开始，经验难复用
```

主要成本不是某一个步骤很难，而是：

- 客户服务需求没有标准化为 Service Package；
- 数据、证据、版本、审批和实际执行没有统一对象；
- 交付人时、返工、客户等待和超范围工作无法量化；
- 黑帽请求可能混入白帽服务流程；
- 结果无法形成可审计的复盘和续费依据。

| Canvas 维度 | v2 判断 |

| 愿景 | 让白帽 ASO 从依赖个人经验的项目制交付，变成证据化、可审批、可验证、可复购的服务能力 |

| 关键取舍 | 先做客户服务和内部交付闭环，后做多市场、白标、API 和高自治执行；不做排名/黑帽能力 |
| 关键指标 | 首次可审时长、一次通过率、Evidence 覆盖率、SLA 达成率、复购信号、安全红线事件 |
| 增长路径 | 内容/免费诊断或已有客户关系 → 诊断包 → Listing/本地化迭代 → 周期服务 → 代理商/白标 |
| 核心能力 | ASO 专家、数据连接、Evidence Object、Policy Gate、工作流、客户成功和审计 |
| 防御性 | 经授权的交付案例、专家修改反馈、版本/验证/学习数据和可复用服务 SOP，而不是模型名称 |

#### 建议的白帽服务包

| 服务包 | 适用任务 | 主要交付物 | 一期状态 |
| --- | --- | --- | --- |
| 白帽健康诊断 | 客户不知道问题在哪里 | 诊断、证据包、缺口清单、优先级和下一步建议 | 首个验证包 |
| 新市场诊断与商店页迭代 | 进入单一新市场 | 市场/竞品、关键词/评论、Listing Version、Creative Brief、本地化审校和验证计划 | 首个可卖方向 |
| 评论与 VoC 洞察 | 评分、痛点或需求变化 | 主题、原话证据、版本/时间分层、产品问题与商店表达问题区分 | P0 组件 |
| 受控验证与复盘 | 有基线且希望检验一个主假设 | Experiment Card、实际版本对账、观察窗口、Outcome Report | P1 |
| 周期性白帽增长服务 | 持续迭代和复购 | 机会队列、版本迭代、评论/竞品监测、月度复盘 | 二期 |
| 代理商/白标交付 | 多客户批量交付 | Partner Workspace、模板、权限、白标报告和审计 | 三期，不作为一期主战场 |

这个方向的最大假设是：客户愿意为“诊断 + 可审交付物 + 审批 + 复盘”付费，而不是只接受排名、安装或评论保证；必须先用 concierge 服务和真实工时验证。

## **AI 技术应用方向初步探索**

**目的：** 说明 AI 如何同时帮助客户受理和内部交付，但不把 AI 作为销售包装，也不替代专家、客户审批和平台责任。

### 为什么需要 AI？

#### AI 适合处理多语、非结构化和多模态市场信号

评论、标题、长描述、截图、竞品页面、服务请求和客户反馈不是统一表格。AI 可以做多语语义聚类、需求归纳、产品事实对照、文案草案和证据解释；但第三方估算不能被生成模型改写成真实指标，相关性也不能直接写成因果。

#### AI 能把“客户想要什么”映射到“服务团队交付什么”

Agent 的第一步不是生成文案，而是识别：App、商店、国家、语言、目标、当前状态、授权数据、截止时间和风险。基于完整性检查，它可以给出诊断、补件清单和 Service Package 候选，避免客户直接提出无法定义的“帮我增长”。

#### AI 可以把跨角色交付上下文保留下来

客户、ASO、母语、本地化、设计、服务经理和数据人员共享 Evidence、Listing Version、Review、Approval、SLA 和 Outcome 状态，AI 在这些结构化上下文中工作，比独立聊天更不易遗忘版本和责任。

### AI、规则和人工的职责边界

| 参与方 | 负责内容 | 不负责内容 |
| --- | --- | --- |
| 客户侧 Agent | 受理、补件、诊断解释、服务匹配、状态问答、审批提醒 | 承诺排名/下载、代表客户批准或发布 |
| 内部交付 Agent | 证据检索、评论/关键词聚类、草案、任务拆解、版本比较、QA 提示、报告初稿 | 自主扩大范围、绕过 Policy Gate、直接写入商店 |
| 数据工具/连接器 | 拉取公开页、评论、关键词、趋势和授权后台快照 | 自行把数据变成业务因果结论 |
| 规则与 Policy Gate | 字符、必填、禁用词、产品事实、权限、风险、状态和审批门槛 | 处理所有复杂语言、文化和商业判断 |
| ASO/本地化/设计专家 | 策略、品牌、母语、创意和最终 QA | 重复搬运所有基础数据 |
| 客户审批者 | 范围、品牌、版本、发布授权和执行责任 | 把 Agent 建议视为平台或业务保证 |

### 初步技术路径设想

```text
客户入口与项目上下文
+ 固定服务工作流
+ 多语模型与多模态模型
+ Evidence Object / Product Fact Store
+ 公开与授权数据连接器
+ Policy Gate / 规则校验
+ 人工 Review / Customer Approval
+ Validation / Outcome / Learning 回流
```

不建议让多个 Agent 自由讨论后直接输出“最佳策略”。受理、诊断、服务匹配、交付、审批和复盘属于相对稳定的工作流；AI 只在需要理解、生成、分类和解释的节点发挥作用。

### 技术架构设想

```text
客户提交 App、商店、国家、目标、预算/时间约束和授权信息
↓
Tenant / Account / App Workspace / 权限与数据完整性检查
↓
Policy Gate：识别排名保证、刷安装、虚假评论、越权数据等高风险请求
↓
Service Match：诊断、Listing/本地化、评论洞察或复盘服务包
↓
公开/授权数据快照：商店页、评论、竞品、关键词、规则、产品事实
↓
Evidence Object：来源、时间、市场、语言、口径、支持主张、置信度、局限
↓
内部 Delivery OS：Growth Task、专家路由、SLA、草案、QA、Review
↓
Customer Approval：版本差异、修改轮次、审批人和执行授权
↓
人工发布/验证：实际版本、观察窗口、指标、干扰因素
↓
Outcome Report / Learning：继续、补数据、调整、复购或停止
```

### 主要模块设计

| 模块 | 核心功能 | 主要输出 |
| --- | --- | --- |
| Customer Account / App Workspace | 客户、App、商店、市场、角色、授权和可见性 | 租户上下文和数据边界 |
| Service Intake / Match | 采集目标、现状、资料和期限，识别服务包 | Service Request、补件清单和匹配理由 |
| Market / Competitor Research | 市场、竞品定位和商店页差异 | 机会卡、对标证据 |
| Review / VoC Insight | 多语评论清洗、主题、情绪、版本和原话 | 用户问题与产品/商店缺口 |
| Keyword / Listing Strategy | 搜索意图、元数据、字符和产品事实校验 | Listing Version、建议理由和风险 |
| Creative / Localization Brief | 截图/视频卖点、顺序、本地化和术语 | Creative Brief、母语待确认项 |
| Delivery OS | 任务、专家路由、SLA、QA、交接和客户沟通 | Deliverable、状态时间线、审计 |
| Review / Approval | 内部 Review、客户修改/批准/退回 | Approval 记录和实际执行授权 |
| Validation / Outcome / Learning | 版本、窗口、指标、干扰、结论和适用条件 | Outcome Report、下一任务候选 |
| Policy Gate | 拒绝、合规替代、人工升级和隔离线 | 风险事件、拒绝理由、审计日志 |

### 可落地的 3 个子场景

#### 子场景一：客户诊断与服务匹配

客户输入“已有 App 在某市场自然增长停滞，希望优化商店页”。Agent 先问商店、国家、语言、目标指标、近期版本、产品事实和授权情况；然后输出只读诊断、证据缺口、风险和服务包候选。客户可以选择健康诊断、Listing 迭代或评论/VoC 洞察，而不是直接收到不可执行的长报告。

#### 子场景二：专家交付与客户审批

内部交付 Agent 将获批范围拆成 Growth Task，关联 Evidence Object、Listing Version、Creative Brief 和 SLA；ASO、母语和设计专家在同一上下文中修改并留下理由。客户看到版本差异、来源、风险、待确认产品事实和执行责任，完成 Approval 后由客户或授权人工发布。

#### 子场景三：结果复盘与续费/复购

系统对账实际发布版本与计划版本，记录观察窗口、指标口径、广告/产品/季节等干扰因素，并生成证据等级正确的 Outcome Report。下一项服务应来自未解决的增长任务、结果学习或新市场需求，不根据虚假的排名保证自动推销。

### 可行性与风险评估

### **数据可行性**

第一阶段可以使用：

| 数据 | 可得性 | 用途 | 风险与边界 |
| --- | --- | --- | --- |
| Google Play/App Store 公开页 | 高 | 竞品、定位、文案和素材观察 | 记录采集时间、地区和页面状态 |
| 公开用户评论 | 高 | 需求、痛点、语言和版本线索 | 抽样偏差、隐私、虚假评论，不作总体因果 |
| 公开趋势/关键词建议 | 中高 | 搜索意图和市场变化参考 | 不等于平台真实搜索量 |
| 第三方 ASO 数据 | 需确认 | 关键词、竞品和市场补充 | 权限、许可和估算口径必须展示 |
| 客户商店/分析后台 | 需授权 | 真实 CVR、版本、实验和结果 | 商业敏感、租户隔离和删除权 |
| 历史服务/实验记录 | 需补充 | 复用和评估 | 需要脱敏、适用范围和客户授权 |

PoC 可以使用公开数据和模拟任务，但模拟结果必须与真实数据、客户事实和平台指标明确区分。

### 技术可行性

1. 多语模型可以处理评论主题、搜索意图和本地化草案；
2. 多模态模型可以分析截图、视频和图文一致性；
3. RAG/规则库可以为平台规则、产品事实、术语和风险提供引用；
4. 结构化对象和工作流可以控制租户、版本、权限、SLA 和审批状态；
5. Agent 工具调用可以连接公开数据、授权后台、任务系统和报告模板；
6. 一期不需要训练排名预测或实时竞价模型；
7. 人工审核和人工执行可以把外部写入风险控制在受控范围。

### 业务风险

| 风险 | 表现 | 初步控制 |
| --- | --- | --- |
| 黑帽/白帽定位冲突 | 客户以排名、安装、评论保证为购买条件 | 受理前 Policy Gate、拒绝清单、合规替代包和隔离人工线 |
| 客户期望错配 | 客户以为 Agent 已发布或保证结果 | 每个状态显示责任人、授权、Approval 和执行状态 |
| 证据幻觉 | 生成不存在的搜索量、功能、排名或引用 | Evidence Gate、产品事实库、来源校验、正确拒答 |
| 结果归因过度 | 把前后变化写成文案或服务包的确定因果 | 实际版本对账、观察窗口、干扰记录和证据等级 |
| 本地化质量不足 | 语法正确但不自然、文化误用或品牌偏离 | 母语/品牌专家 Review、术语库和文化风险集 |
| 数据越权/跨租户 | 客户资料或授权数据混用 | ACL、租户隔离、缓存/导出审计、红队回归 |
| 服务毛利不足 | 定制和审核成本高于 Agent 节省 | 先做 concierge，按人时、返工、SLA 和范围测算 |
| 平台政策变化 | 规则、字符或实验能力变化 | 官方来源版本化、失效提醒和人工复核 |

### 初步成功标准

#### PoC 阶段

- 能对一个 App、一个商店和一到两个市场生成完整、可追溯的诊断与交付包；
- 客户能理解服务范围、证据、版本、风险、审批和人工执行责任；
- 重要主张绑定 Evidence Object，不把模拟、估算和推断写成事实；
- 能生成包含假设、主变量、指标、窗口和停止规则的验证计划；
- 具备高风险请求识别、拒绝、人工升级和审计记录；
- 不出现自动发布、虚假增长结果或黑帽执行建议。

#### 真实白帽试点阶段

- 首次可审交付时长、客户补件轮次、专家实质返工率和交付人时有基线；
- 客户能完成一次 Approval，内部能按约定 SLA 交付；
- 实际发布版本、观察窗口、指标口径和干扰因素可对账；
- Outcome Report 能区分观察、实验支持、专家判断和无法归因；
- 客户出现继续服务或复购信号，但不把复购等同于业务效果已证实；
- Policy Gate 红线事件、越权和跨租户泄露为零。

## **业务流程/场景分析**

**目的：** 展示客户购买、内部交付和结果复盘如何在同一对象链上运行，以及哪些环节仍由人工负责。

### 当前业务流程图

```mermaid
flowchart LR
    A[客户提出模糊增长诉求] --> B[销售/客户经理人工判断范围]
    B --> C[ASO运营分别查关键词、竞品、评论和商店页]
    C --> D[表格/文档整理与专家凭经验决策]
    D --> E[本地化、设计和ASO多轮返工]
    E --> F[聊天/邮件中交付并等待客户审批]
    F --> G[客户或内部人工发布/实验]
    G --> H[人工观察结果与编写报告]
    H --> I[版本、证据和学习散落在不同地方]
    I --> J[下一项目重新开始或转向不可控结果承诺]
```

当前流程的主要问题：

- 购买对象和服务范围不清；
- 研究数据、产品事实和策略建议无法稳定追溯；
- 客户 Approval、内部 Review 和实际发布责任容易错位；
- 交付人时、返工、SLA 和超范围工作不可见；
- 黑帽请求可能混入白帽服务；
- 结果不能稳定转化为下一项白帽任务。

### 引入 AI 后的理想业务流程图

```mermaid
flowchart LR
    A[客户提交App/商店/市场/目标/授权] --> B[Account与数据完整性检查]
    B --> C[Policy Gate与高风险请求识别]
    C --> D[诊断与Service Package匹配]
    D --> E[公开/授权数据快照]
    E --> F[Evidence Object与Growth Task]
    F --> G[内部Delivery OS：专家路由/SLA/草案/QA]
    G --> H[Listing Version/Deliverable Review]
    H --> I[客户Approval与执行授权]
    I --> J[客户或授权人工发布/验证]
    J --> K[Outcome Report：窗口/指标/干扰/证据等级]
    K --> L[Learning：继续/调整/补数据/复购/停止]
```

AI 主要增强：

- 受理信息补全、服务匹配和状态解释；
- 多语评论、关键词、竞品和素材的语义理解；
- 证据关联、文案/Creative Brief 草案、版本差异和质量检查；
- 任务拆解、专家路由、SLA 提醒、报告初稿和学习候选。

人工保留：

- 服务范围、价格、SLA 和客户承诺；
- 市场优先级、产品事实、品牌和母语质量；
- 客户 Approval、商店发布、实验启动/停止和结果采纳；
- 法务/平台合规最终判断；
- 高风险请求的拒绝、升级、隔离和事件复盘。

## 本轮需要重点讨论的 6 个问题

1. **一期首要用户是否确认：** 是否先服务已有 App、增长停滞或进入单一新市场的中小开发者/增长负责人，代理商是否放到二期/三期？
2. **首个服务包：** 是否以“白帽 ASO 新市场诊断与商店页迭代交付包”作为第一款可售卖服务，而不是泛化的 AI Agent？
3. **首个商店与市场：** 是否采用 Google Play + 一个或两个目标市场作为一期，保留 Store-Country 可扩展数据模型？
4. **项目性质与可写范围：** 最终按真实业务升级、概念方案还是个人 PoC 呈现；哪些客户、价格、结果和公司能力可以公开？
5. **白帽/黑帽组织边界：** 存量高风险业务是否隔离为人工服务线，谁承担销售、合规、数据、权限和事件责任？
6. **MVP 深度：** 第一版是否止于“客户入口 + 内部交付 OS + 证据化诊断/交付/复盘”，在何种 Gate 通过后才开放连接器、客户自助、API/白标或受控自动化？

在以上问题确认并完成 E1—E5 试点前，本文件作为方向讨论 v2，不进入大规模 PRD 工程化或对外效果承诺。
